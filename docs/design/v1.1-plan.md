# 實作計畫：v1.1（T-40、T-42、T-43、T-44、T-48）

依據：[v1-core.md](v1-core.md) 第 2.4、3.7、8 節 ②，以及 PM 交辦的四項。從 v1.0.0（`main` 的 b6487e3）開始，只在本機 commit，不 push、不打 tag；版號由 PM 推版時決定（預計 1.1.0），CHANGELOG 先寫在 `Unreleased`。

## 共同做法

- 開發準則照舊：修 bug 先寫重現測試；測試失敗就改程式，不改測試，改既有測試要逐項寫理由（寫在 commit 訊息和最後的報告）；一個 commit 只做一件事；路徑一律經過 `plainLocalPath`；Windows 上啟動外部程式一律用完整路徑（`core/src/host.ts` 的 `run`）；不放寬任何安全檢查。
- 每個里程碑結束：core 的 `npm test`、`npm run typecheck`，`claude plugin test .`，`claude plugin validate .`，都看 exit code，全過才 commit。
- 示範和測試資料一律用 Acme，資料路徑用 `PROJECT_PM_HOME` 和暫存的家目錄，不碰使用者真正的 `~/.project-pm/`、`~/.claude/project-pm/`、`~/.claude.json`、`~/.claude/settings.json`。
- 會輸出文字的測試，中英文各跑一次。

## 實作前查證的事實（2026-11-21，Claude 桌面版 6.6395.0、Claude Code 2.1.326）

- 桌面版啟動的 `claude.exe` 帶環境變數 `CLAUDE_CODE_HOST_SESSION_ID=local_…`（就是 mod 從 `get_session` 拿到的 id）、`CLAUDE_CODE_ENTRYPOINT=claude-desktop`、`CLAUDE_CODE_SESSION_ID=<CLI 的 Session id>`。在這個 Session 的 Bash 子行程實際看到。MCP server 和 hook 也是 `claude.exe` 的子行程，會繼承同一份環境（v1.0 已實測 MCP 子行程有 `CLAUDE_CODE_SESSION_ID`）；桌面版的 MCP 子行程本身沒有實測，見 M3 的「沒驗證到的」。
- mod 的 `$.fs` 只有 `read`、`write`、`list`、`exists`、`stat`、`ancestors`：沒有刪除、改名、獨佔建立，做不到核心的「鎖 → 暫存檔 → rename」。

## 設計決定（T-40）

設計文件 2.4 節的 E2 寫「mod 透過核心的純函式讀寫新路徑，也照樣寫回舊路徑」。上面第二點使得 mod 自己寫新路徑時不能加鎖、也不是原子寫入：核心讀到寫到一半的檔會當成資料損毀（`StoreError`），而且依規定不會覆蓋它，看板會一直壞到有人修。所以分成讀和寫：

| | 做法 | 理由 |
| --- | --- | --- |
| mod 讀 | 新路徑和舊路徑都讀，用核心的純函式 `mergeLegacy` 合併（從 `core/src/store.ts` 抽成不碰 Node 的 `core/src/merge.ts`） | 和核心看到的一模一樣 |
| mod 寫（有核心） | 交給核心：`$.mcp.call('project-pm', …)`。認領、卸任用 `pm` 工具。提示列的「不要 PM」照舊寫舊路徑（只是一個旗標，核心讀取時依「後寫的為準」合併，不需要為它在模型看得到的 `pm` 工具加一個動作） | 鎖、合併、雙寫都在核心做，只有一份程式 |
| mod 寫（沒有核心，或呼叫失敗） | 照 v1.0 寫舊路徑 | 核心讀取時本來就會合併舊路徑（E1，已有測試），不會遺失 |
| 遷移 | 自動：核心第一次寫入時，新路徑就由「新＋舊」合併而來；沒裝核心的使用者資料留在舊路徑，裝了核心後直接讀得到 | 不需要使用者做任何事 |
| 回切 | 核心每次寫入都把完整內容寫回舊路徑（E1 雙寫），所以退回 v1.0 的 mod 或移除核心，舊路徑仍完整 | 2.4 節 |

其他：

- **偵測核心**（3.7 節）：mod 讀 Claude Code 的 MCP 設定（`~/.claude.json` 使用者層級的 `mcpServers`，以及這個專案的 local 設定），有 `project-pm` 就是「有核心」；Session 中途才連上的，也以工具清單裡有 `mcp__project-pm__pm`（只有核心有 `pm`）為準。
- **身分**：核心在桌面版用 `CLAUDE_CODE_HOST_SESSION_ID`（`local_…`）當 actor id，所以核心記的 PM、負責人、驗收者和 mod 是同一個 id，舊資料不用改。mod 另外把 `claude-code:<自己的 transcript id>` 也認成自己，萬一 MCP 子行程沒拿到 `local_…` 也不會認不出 PM。
- **Session 清單**（3.2 節「桌面版給 list_sessions」）：mod 本來就把每輪結果存在 `~/.claude/project-pm/rounds/<id>.json`（Session 清單、最後一句話、CI、push）。核心的看板在 PM 是桌面版 Session 時讀 PM 的 round 檔和舊路徑的 `sessions/<id>.json`，並合併核心 actor 裡同一個 id 的回報。mod 在模型呼叫 board、結案前先更新一輪，再讓核心回答，所以看板不會舊。round 檔超過 10 分鐘沒更新（桌面版沒開），就不再當成有人在執行。
- **hook 不重複**：桌面版有 mod 時，核心的 Claude Code hook 讓位（mod 已經用 `prompt.compose` 放交付指示和準則、記任務清單）；CLI 照舊由核心的 hook 處理。mod 在沒有桌面版 Session id 的地方（CLI）而且有核心時，也不再放交付指示，交給核心的 hook。
- **Agent 只能讀 ledger**：mod 照樣攔 PM 的 Agent 呼叫 `ledger` 的 add、update；其他交給核心。
- **init**：v1.1 起裝了 mod 也照樣加 MCP 設定和 hook（3.7 節：E2 之後不會撞名）。

驗收條件：

1. 新安裝：`init` 後 `CLAUDE.md` 有段落、沒有 `AGENTS.md`；`uninstall` 後每個檔和安裝前逐位元相同（沒有 `CLAUDE.md`、已有 `CLAUDE.md`（含 CRLF）、已有自己的 `AGENTS.md` 三種）。

### M2 T-40：核心認得桌面版 Session

- 身分：MCP 連線和 hook 在 `CLAUDE_CODE_HOST_SESSION_ID` 是 `local_…` 時用它。
- 看板和結案檢查的 Session 來源：PM 是桌面版 Session 時，讀它的 round 檔和舊路徑的 Session 檔，並合併同 id 的核心 actor（回報）；PM 的 Agent 紀錄也從舊路徑讀。
- 核心的 hook 在桌面版、mod 已安裝時讓位。

驗收條件：

1. 有 `CLAUDE_CODE_HOST_SESSION_ID=local_x` 時，MCP 的 `pm claim` 記下 `local_x`；hook 寫的 actor 也是 `local_x`；沒有時和 v1.0 相同。
2. 用 Acme 的 round 檔和 Session 檔：核心的 board 列出桌面版的 Session 和狀態（含「等你回覆」「CI 失敗」），文字和 mod 自己畫的一致；結案檢查用得到 round 的最後一句話；round 過期時不算執行中。
3. 桌面版＋mod：hook 不寫 actor、不輸出任何東西；CLI：和 v1.0 相同。

### M3 T-40：mod 改用核心

- 偵測核心（上面「偵測核心」）。有核心時不註冊 board、ledger、report，攔到這三個工具時先更新一輪再交給核心回答（Agent 改 ledger 照樣擋）。
- 讀專案：新路徑＋舊路徑，用 `mergeLegacy`。寫：有核心時經核心，否則（或失敗時）寫舊路徑。
- Session 卡片讀得到核心 actor 的回報（模型用核心的 `report` 回報時）。
- 沒有核心時，行為和 v1.0 完全相同。
- `init`：裝的 mod 是 1.1 以上（依版本號判斷，2.4 節）時也加 MCP 設定和 hook；更舊的 mod 照 v1.0 不加，並提示更新。
- mod 在用核心時，每 4 分鐘至少重寫一次 round 檔（內容沒變也寫），核心才不會把它當成桌面版已關閉；沒有核心時照舊只在內容變了才寫。

驗收條件：

1. 原有的 `claude plugin test .` 測試全過（沒有核心的情況）。
2. 有核心時：mod 不呼叫 `tool.register`；`/pm` 經 `pm claim`、`/pm off` 經 `pm release`；呼叫失敗時寫舊路徑。
3. 雙寫不遺失（並列測試，用核心的程式和 mod 的寫法輪流寫同一個專案）：核心寫 → mod 讀得到核心欄位（`uid`、`rev`、`commits`、`qa.byPerson`）；mod（v1.0 寫法，寫舊路徑）寫 → 核心讀得到、核心欄位補回；交替 20 次後每一項的每個欄位都在。
4. 回切：上面的流程之後，舊路徑的檔單獨拿出來，v1.0 的 mod 讀得到每一項（舊格式的欄位都在）。

### M8 T-48 額度管理（上下文大小、自動壓縮、自動交接）

起因：使用者回報 token 用得太快。實測最大的消耗是 PM 和實作 Session 的上下文太大：每一輪都要把整段上下文讀一次，閒置超過 1 小時再喚醒，整段要重寫進快取。

原則（使用者 2026-11-21）：目標使用者是 Vibe Coder，**額度由 PM 自己管，不丟給使用者**。每一項依序找做法：① mod 或 Claude Code 自動做；② PM 在對的時機自己做；③ 前兩種都做不到，才請使用者動手，而且只能是白話一句加一個按鈕（例如「點這裡整理一下對話，可以省下約 8 成額度」），不叫使用者打指令。

**B 的細節**
- 只在 PM 的 mod 實例、只在主迴圈做；同一次超過門檻只壓縮一次（壓縮後上下文變小，自然不會再觸發；失敗就記下，10 萬 token 內不重試）。
- 壓縮指示（`instructions`，也在 PM 的 `session.compact` hook 裡補給所有觸發方式）：「保留：進行中的工作項目和負責的 Session、使用者還沒回覆的問題、這次對話裡使用者做的決定和偏好、正在等的回報。看板和交辦清單隨時能用 board 重讀，不必保留細節」。
- 壓縮前後各記一筆到 PM 的 track（`tokensBefore`、`tokensAfter`），看板的 PM 卡片顯示「已自動整理對話：31.0 萬 → 2.1 萬」。
- 正在等使用者回覆（PM 的上一輪以問句結束）時也可以壓縮：壓縮保留最近的訊息（實測 transcript 的 `preservedSegment`）。
- **PM 自我交接**（(b) 和 `/compact` 都不成立時）：PM 的上下文 ≥ 壓縮門檻時，mod 在 PM 的 `prompt.compose` 加指示：先確認每個進行中的工作項目在 ledger 裡的負責人、狀態、備註都是最新的，再照交接範本寫 PM 交接筆記（`~/.claude/project-pm/reports/<專案>/pm-handover-<時間>.md`：進行中的交辦、等誰回報、使用者還沒回覆的問題、使用者這次對話裡的決定和偏好），然後用 `start_session`（`fresh`）開新的 PM Session，brief 只有「你是〈專案〉的 PM，先讀交接筆記〈路徑〉，再用 board 看最新狀態」。新 Session 的 mod 看到 brief 裡的交接標記就自動認領 PM（核心的 `pm claim` 加 `handover_from: <舊 PM id>`：只有舊 PM 自己開的 Session 才能接手，舊 PM 隨即卸任），之後子 Session 的回報都送到新 PM。舊 PM 回使用者一行「對話太長了，我換到新的 PM 對話繼續：[〈標題〉](#local_…)」。`start_session` 只能在使用者發話的那一輪做（第 8 項），所以排到使用者下一次發話時：先交接，再由新 PM 回答那則訊息（brief 附上使用者的原話）。

**自動交接流程（C）**
1. 偵測：PM 的 mod 每輪（`refresh`）讀到某個實作 Session 的上下文 ≥ 交接門檻（預設 200,000），而且它還有工作（任務清單有未完成的步驟，或負責的工作項目還開著）。閒置中、被內建閒置壓縮處理過（`compactedTo` 有值、小於門檻）的不算。
2. 請它寫筆記：
   - 它正在執行：mod 在它自己的 `prompt.compose` 加一句「你的上下文已 21.3 萬，超過交接門檻：在下一個里程碑段落停下來，照交接範本寫筆記，回報 PM」。不用 PM 出手。
   - 它閒置中：PM 的 mod 用 `$.prompt.submit` 對 PM 開一輪（mod 的名義，不是使用者），PM 用 `SendMessage` 請它寫交接筆記（喚醒成本照算，這筆是必要的花費；它已閒置超過 1 小時而且工作已到段落時，改由 PM 直接讀它的最後回報和 `list_events` 自己寫筆記，不喚醒它）。
3. 開新 Session：它回報「[交接, sha] …」後，PM 用 `start_session`（`fresh`，brief 只放筆記路徑和還沒做的事）。這一輪若是由別的 Session 的訊息開始的，桌面版會拒絕；mod 就把它記成「待開的交接」，在使用者下一次對 PM 發話時，由 `prompt.compose` 提醒 PM 先開好這些 Session（這是使用者交辦的工作，不需要再問）並用一行告訴使用者。
4. 舊的 Session：PM 把工作項目的負責人改成新的 Session；舊的照既有規則（沒有待辦、沒有開著的 PR）才封存，封存要問使用者。

**喚醒成本（D）**
- 估算：閒置超過 1 小時（快取過期，整段重寫）＝上下文 × 1.3；1 小時內＝上下文 × 0.1。1.3 用 T-30 的實測：65 萬的上下文喚醒約 84 萬（輸入等價 token）。倍數寫成一個常數，之後有新的實測再改。被內建閒置壓縮處理過的，用 `compactedTo` 代替上下文。
- PM 的 mod 在 PM 自己的主迴圈呼叫 `SendMessage` 給閒置中、喚醒成本 ≥ 10 萬的 Session 時，第一次回 `deny`，理由寫給 PM 看：「喚醒〈名稱〉約要 X 萬。小事改開新 Session（約 7 萬）或 Agent（約 6～15 萬）；這件事需要它的上下文就原樣再送一次」。同一個收件者、同樣內容 10 分鐘內再送就放行。使用者看不到這段，決定由 PM 做。這是額度提醒，不是安全檢查，不影響任何既有的檢查。
- 看板（文字、面板、網頁）照樣顯示數字，但 PM 規則寫明「不必把這些數字列給使用者，你自己決定」。

#### 功能清單

1. **Session 卡片**（面板、網頁看板、文字看板；包括 PM 自己）多一行小字：「上下文 21.3 萬・閒置 2 小時・喚醒約 27.7 萬」（英文「context 213k · idle 2h · wake ≈277k」）。執行中寫「上下文 21.3 萬・執行中」；沒有資料的那一段不顯示。中文以萬為單位、一位小數；英文以 k 為單位、整數。
2. **需要處理**：只列 PM 要做、還沒自動完成的事：「[交接中] 〈名稱〉上下文 21.3 萬：等它寫好筆記」「[待開交接] 〈名稱〉的筆記好了，下一輪開新 Session」。B 的退路 2 才在面板顯示按鈕。這些是 Session 的狀況，不算進 M4 的工作項目分類，也不擋結案。
3. **門檻**：預設交接 200,000、壓縮 300,000，可設定：`/pm context <交接> <壓縮>`（例 `/pm context 200k 300k`；不帶參數顯示目前值；`default` 恢復）。存在和開發準則設定同一個地方（mod 的設定，以及核心的 `~/.project-pm/config.json` 的 `context: { handoff, compact }`）。接受 100k～1,000k（100k 是 Claude Code 自己壓縮門檻的下限）。一般使用者不用碰。
4. **交接筆記範本**：`core/templates/handover.md` 和 `handover.zh-TW.md`。欄位：一行狀態 `[交接, <最新 sha>] <一句話>`；分支、最新 commit、工作樹是否乾淨；已完成（每個里程碑一行：代號、sha、一句話）；進行中（做到哪、下一步具體到檔案和函式）；待決定；已查證的事實（附依據，接手的人不用再查）；陷阱（試過不行的做法）；驗證（要跑的指令和該看的 exit code）。不超過約 150 行，詳細內容放報告檔，筆記只放路徑。
5. **PM 規則**（`role.text`，中英文同步）：
   - 新增「額度」：上下文由 mod 自動管理；看板出現「交接中」「待開交接」時照自動交接流程做，不要叫 Session 一路做到結束，也不要問使用者要不要交接。不要叫使用者打 `/compact` 或任何指令。
   - 改第 10 條：喚醒成本看看板上的「喚醒約 X 萬」，自己決定喚醒還是開新的，不把數字列給使用者。刪掉舊的固定實測數字。
   - 改第 13 條 QA：以推版為單位批次做。小修正（只改文件、或單一檔案的小修）PM 看 CI 和 diff，記 `qa skip`，qa_note 寫「小修正：CI 通過、已看 diff（sha）」；功能變更等推版前開一個完整的 QA Agent，一次涵蓋這一版所有待 QA 的項目，逐項記 pass 或 fail。推版前一定要做這次完整 QA。
6. **子 Session 的交付指示**（`role.delivery`）加一句：「PM 請你交接時，照範本寫筆記（路徑：…），回報第一行 `[交接, sha]`」。
7. **ledger update 只回一行**：mod（`hooks/actions.ts:1485`）和核心（`core/src/tools.ts:239`）只回「已更新 T-12（owner、qa）。」，列出改了哪些欄位，不附整列；核心的 structured 只留 `{ id, rev, revision }`。`add`、`list` 不變。

#### 實作的第一步：在桌面版實測

M8 開工時，先在桌面版用 Acme 測試專案實測下面三項，結果寫進報告，再決定 B 走哪一條（`-p` 的結果已在第 6 項：`$.session.compact()` 被拒）：

1. 桌面版 Session 裡 `$.session.compact()` 成不成功（看 `tokensAfter`，以及 transcript 有沒有 `compact_boundary`）。

3. 由 mod 的 `$.prompt.submit` 開始的那一輪，`start_session` 是否被拒（決定 C 第 3 步要不要排到下一輪）。

#### 驗收條件

1. 單元測試（中英文各一）：數字格式（萬／k）；閒置時間；喚醒成本的兩段公式（× 1.3、× 0.1）和 1 小時邊界（59 分、61 分）、`compactedTo` 優先；上下文來源的順序（`get_usage` 比 track 新時用它 ＞ track ＞ 不顯示）；略過子 Agent 的 `turn.complete`；核心讀 transcript 檔尾時略過 `isSidechain`、最後一行不完整、沒有 usage 的情況。
2. 自動壓縮（假的 `$.session.compact`、`$.prompt.submit`）：PM 299,999 不動、300,000 壓縮一次；`compact` 被拒時改用 `submit`；兩者都失敗時不重試、改走 PM 自我交接（`prompt.compose` 多那段指示；使用者下一次發話時開新 PM；`pm claim` 的 `handover_from` 只接受舊 PM 開的 Session，其他 Session 拿它認領會被拒）；自我交接也失敗才出現按鈕；非 PM 的 Session 永遠不壓縮；輪次進行中不呼叫。
3. 自動交接：執行中的 Session 在 200,000 時 `prompt.compose` 多那一句、199,999 沒有；閒置中的大 Session 讓 PM 被 `$.prompt.submit` 叫起來一次（不重複）；`start_session` 被拒時記成「待開交接」，下一次使用者發話時提醒 PM。
4. `SendMessage` 擋一次：閒置 2 小時、上下文 10 萬，第一次擋下、理由含「喚醒約 13.0 萬」；10 分鐘內原樣再送放行；換內容再擋；1 小時內閒置、喚醒成本 < 10 萬、子 Agent 呼叫都不擋。
5. 按鈕的退路：寫進 `settings.local.json` 只動 `autoCompactWindow`，其他內容逐位元不變；uninstall 還原；不按就不寫。
6. ledger update 的回覆只有一行，含改過的欄位名；mod 和核心的字串相同（測試比對）。
7. 面板和網頁看板在瀏覽器實際看過（375px、1280px，淺色、深色）：新的一行不擠壓卡片、不水平捲動。
8. 「實作的第一步」三項的實測結果寫進報告；既有測試全過；要改的既有測試（例如斷言 update 回覆含整列的）逐項寫理由。
