## [1.2.0] - 2026-11-21

### Added
- One-click setup from the desktop board (T-51). With the board open in a project that is not set up, the mod gets the core of its own version from this repository's GitHub release and checks it against the release's `SHA256SUMS`, then shows one sentence, the list of changes `init` would make, and **Set up** (設定); the press runs `init --yes`. Once set up, **Remove setup** (移除設定), asked once more, runs `uninstall --yes`. The person downloads nothing and types no command. The mod's own `$.http.fetch` and `$.fs.write` carry text only, so the download goes through the system's own curl, by its full path (System32 on Windows, `/usr/bin` on macOS and Linux), one hop at a time: every address must be https on `github.com`, `objects.githubusercontent.com` or `release-assets.githubusercontent.com`, redirects are followed by the mod only to those hosts, and a size cap holds (200 MB for the program, 64 KB for `SHA256SUMS`). `SHA256SUMS` itself comes through `$.http.fetch`, before any curl runs, so the organization's web-fetch policy still decides: when it refuses GitHub, or GitHub can't be reached, no curl runs, and the card names the Releases page as the way by hand. While it downloads, the card says so (version, about how many MB, GitHub, system curl); once ready, it says what was downloaded and checked. A program is run only once its SHA-256 matches, and is checked again right before `init --yes`; a mismatch, or a download cut short, empties the file. The program waits in the mod's data folder until `init` copies it into `~/.project-pm/bin`. Offline, blocked by policy, a failed or too-large download, a mismatch, or a folder that is not a git project each get one plain sentence and **Try again** (重試). The session that set up keeps the mod's own tools; sessions started after it use the core's.
- A double-click on the program (T-52). With no arguments and stdin a terminal, as in the console window Windows opens, it lists what `init` would change and waits: Enter sets up (`init --yes`), closing the window cancels. Set up already, it opens the board (`open`). Outside a git project with nothing set up, it says so and points to Set up on the desktop board first, then to putting the program in the project folder. Set up from a downloaded program, it says the program is now copied to `~/.project-pm/bin`, so the download can be deleted and is not committed. Each ends with "Press Enter to close" (按 Enter 關閉), so the window no longer flashes and closes. With stdin not a terminal it prints the usage and ends with 1, as before.
- `project-pm init --json` and `uninstall --json` print one JSON line (the changes as `init` words them, its notes, what failed), for the mod's setup (T-51).

### Changed
- **Open in browser** without the core points to **Set up**, with a toast, and brings back a setup card that was hidden, so the press never seems to do nothing (T-51). The box no longer links to Releases or tells people to run `init`.
- The READMEs: install the mod, then press **Set up**; the platform table has a row for one-click setup; the overview shows v1.2. The desktop mod and the core are 1.2.0.

### Fixed
- `init` trusted the version Claude Code's `installed_plugins.json` keeps for `project-pm@local-mods`, the version the local copy had when first installed (0.7.0 on a real machine) while the copy loaded was 1.1.0, so it left out the MCP server and the hooks (T-50). That entry is now the local copy, counted by its own `plugin.json`.
- A desktop user has no `claude` on PATH, so `init` said Claude Code was missing and added no MCP server (T-50). It now finds the Claude Code the desktop app ships with, only in the app's own folder (`%LOCALAPPDATA%\Claude-Data\<profile>\claude-code\<version>\<build>\claude.exe`, no link followed; `CLAUDE_CODE_EXECPATH` first when it is one of those), and runs it by its full path; `uninstall` uses the same one.

## [1.1.0] - 2026-11-21

### Added
- The desktop app and the CLI share one ledger and one QA gate (E2, docs/design/v1-core.md 2.4 and 3.7; T-40). The desktop mod finds the core in Claude Code's settings (`~/.claude.json`, user scope or this project's) or by the core's own `pm` tool in the session's tools, and then registers no `board`, `ledger` or `report` of its own: the core answers them, after the mod has refreshed the session list it keeps for the core (the PM's round file, rewritten at least every 4 minutes so the core does not take a quiet desktop app for a closed one). `/pm` and `/pm off` go through the core's `pm` tool; if the core does not answer, the mod writes its own copy as before and the core merges it on read. The mod reads a project from both copies with the core's own merge, and a session's card shows a report made through the core. The PM's agents still may not change the ledger. Without the core the mod works as in v1.0. Nothing to migrate by hand: the core's first write merges the mod's copy, and it keeps writing the mod's copy in full, so going back to a v1.0 mod or removing the core loses nothing.
- The core knows the desktop app's sessions (T-40). In the desktop app it takes the session's own id (`CLAUDE_CODE_HOST_SESSION_ID`, `local_…`), so the PM, owners and checkers it records are the mod's. When a project's PM is a desktop session, the core's board and its close check read the desktop app's session list from that PM's last round, each session's record, last words and CI or push, and the PM's agents; a round older than 10 minutes names the sessions but none counts as running.
- **Open in browser** at the bottom of the desktop pane opens the web board (T-45). If the core's server is running, the system's own opener gets the address; if the core is installed but not running, the core's `open` starts it; if the core is not installed, a box says how to install it, with a link to Releases. The board's private key goes to the browser only, never into the pane's words, its state or a log.
- Each session's context, and what waking it costs, on every card (T-48): "context 213k · idle 2h · wake ≈277k", or "context 213k · running". The pane, the text board and the web board show the same line. Each session's mod records the context its last main-loop turn read; for running sessions the PM also asks the desktop app (`get_usage`) when they have moved; in the CLI, the core's Stop hook reads it from the end of the transcript. Waking a session idle for over an hour is counted at 1.3 times its context (the cache has expired), within the hour at 0.1 times.
- The PM manages its own context without the person (T-48). Past the compaction threshold (300k by default) the PM's mod compacts the conversation between turns, keeping the open work, the person's unanswered questions and decisions, and the reports being waited on; in the desktop app this goes through `/compact`, since an SDK session refuses the direct call. If compacting does not work, the PM is told on the person's next message to write hand-over notes and start a new PM session, which takes the project over only if the old PM started it (`pm claim` `handover_from` in the core). Only if that fails too does the pane offer one button, which sets `autoCompactWindow` in the project's `.claude/settings.local.json` and can be undone. The PM's card shows the last compaction: "Compacted the conversation: 310k → 21k".
- Sessions hand over before their context gets costly (T-48). A session past the hand-over threshold (200k by default) with work left is asked to stop at its next milestone and write hand-over notes by the template (`core/templates/handover.md`, `handover.zh-TW.md`); an idle one wakes the PM once to arrange it. A new session the app would not start in that turn waits for the person's next message. *Needs attention* lists "[Handing over]" and "[Hand-over to start]".
- The PM's message to an idle session that would cost 100k or more to wake waits once, with the cost, for the PM to choose a new session or an agent instead; the same message again within 10 minutes goes through (T-48).
- `/pm context <handoff> <compact>` sets the two thresholds (100k to 1000k each), `/pm context default` resets them; the core reads `context` in `~/.project-pm/config.json` (T-48).

## [1.0.0] - 2026-11-19

### Added
- v1.0's core, `core/` (docs/design/v1-core.md, plan in docs/design/v1-plan.md): one program, `project-pm`, that serves the PM's tools over MCP so Claude Code's command line can use the PM without the desktop app. `project-pm mcp` speaks MCP over stdio, written by hand with no runtime dependency, and offers `board`, `ledger`, `report` and a new `pm` tool (`claim`, `release`, `status`). Every tool takes an optional `project` folder; without it, the first of the MCP client's roots that is a git repository (Claude Code 2.1.326 offers its working folder), else the folder the server runs in. A root the server cannot read (`file:///C:/acme%2Fshop`, or `file://host/path` on Linux and macOS), or roots that are not a list, are left out instead of stopping the server, and one message that goes wrong never stops the ones after it. A session is named after Claude Code's own session id when the server can see it (`claude-code:<id>`), so its tools and its hooks meet on the board. The data lives in `~/.project-pm/` (`PROJECT_PM_HOME` moves it). Every write takes a lock, reads the file again and renames a temporary file over it, and adds one to the project's `revision`. New work items carry `uid` (UUID v7), `createdBy`, `updatedBy` and `rev` (a stable id, who wrote it, and a count of its writes); items written before keep their fields until they change. `ledger` takes `qa_sha` (the commit a verdict checked, full length) and `commit` (a commit of the item). `report` writes the session's record and a detail file, and outside a git repository it says so instead of claiming success.
- `project-pm hook claude-code <event>`: Claude Code's UserPromptSubmit, PreToolUse, PostToolUse and Stop hooks keep each terminal session's last instruction, task list (TodoWrite, and TaskCreate and TaskUpdate as of 2.1.326), background commands and last words, so the board knows where a session stands without it reporting. With a PM, UserPromptSubmit hands each other session the delivery ask and the development guidelines, and PreToolUse keeps the guidelines file from being edited unless the person asked about it. A project's `.project-pm.json` may name only a file inside the repository that git tracks (asked with `git ls-files -z`, so a name with non-ASCII letters, such as `開發準則.md`, or with a quote is found as it is) and that is not in `.git/` (in any letter case, with any trailing dots or spaces, on every system, since Windows and macOS read `.GIT.` or `.GIT` as `.git`), checked both for the name and for the file a link really leads to, so neither an untracked `.env` nor `.git/config` is read, even through a committed link (`RULES.md -> .env`); the person's own `~/.project-pm/config.json` may name any plain local path.
- On Windows the core never starts a program from a folder the project chooses. It looks for each program it names (`git`, `gh`, `claude`) itself, only in PATH's absolute folders on this computer's own disks, and starts it by that full path: not in the current folder, which is often the project's, and not through a `.`, relative or empty PATH entry, which Windows would read against the current folder. Windows' own programs (`cmd.exe`, `rundll32.exe`) come from System32 under `SystemRoot`, taken only when that is a plain local path (else `C:\Windows`), whatever `ComSpec` says. What those programs start by name in turn (the `node` an npm batch file names, `ping` and `notepad.exe` in uninstall's clean-up script) is looked for with the same PATH, its plain local folders only, and with `NoDefaultCurrentDirectoryInExePath` set, so not in their current folder either. A `git.exe`, `gh.exe`, `claude.exe` or `node.cmd` the repository holds is therefore not run, unless the person's own PATH names that folder by its full path.
- Paths from the model or a repository are looked up only when they are plain paths on this computer's own disks, decided from the text alone by one list of what is allowed (`plainLocalPath`): on Windows `X:\…` or a path relative to the session's folder, after `path.win32.resolve`; never a share or device (`\host\share`, `//host`, `\localhost\C$`, `\?\`, `\.\`, `\??\`, `\.\C:\..\UNC\…`, `GLOBALROOT`, `Volume{…}`), a drive-relative or root-relative path (`C:foo`, `\foo`), a stream (`file::$DATA`), a name Windows trims (a trailing dot or space), or a device name (`CON`, `NUL`, `COM1`, …); elsewhere anything but `//…`. Looking up a share would make Windows connect to that host and offer the person's NTLM hash before they allowed anything. Every link on the way is read, not followed, and its target checked the same way. This holds for the guidelines lock (such a path is refused while the lock stands, with a reason that says why), for reading `.project-pm.json`, the file it names and the person's own file, for the MCP tools' `project` (answered with `error.remotePath`), and for `init`'s `AGENTS.md`, `CLAUDE.md` and workflow file. 80,000 generated spellings are checked against Node's and, on Windows, the system's own reading of them on every CI run.
- A change to the guidelines file the person did not agree to is noticed after the fact and warned about; nothing is ever put back. Each session keeps its own baseline of the path the guidelines are set to (the file's SHA-256, whether the path is a link and where it leads, where the file really is), taken when the person speaks in it, in `~/.project-pm/guidelines/` and never in the repository. After each of the session's tools that can write a file (Edit, MultiEdit, Write, NotebookEdit, Bash, PowerShell; init's PostToolUse hook names them), when a notification wakes it and when its turn stops, the path is looked at again. Changed, emptied, deleted, made a link or pointed elsewhere, or now a network path that is not read, without the person agreeing to a guidelines change that turn: the model is told, and the board lists it under *Needs attention* for a week, in both languages, with the session that noticed it, worded as "this session, another session or you may have changed it", and how to undo it by hand: a read-only copy, in `~/.project-pm/guidelines/copies/`, of what the file held when the person last spoke in that session (or later agreed to a change), which a second stray change in the same turn does not move and which is kept for every file the turn has watched, so the guidelines turned off and on again, or the file given up and taken back (`git rm --cached`, `git add`), still point at it; a file the setting comes to name only during the turn gets a copy of what it held then, and the warning says that is not necessarily something the person agreed to; plus `git log -p` for a project's file (given as a command to run only when the file's name has plain characters: letters, digits, `. _ / -` and spaces; a name the repository chose such as `$(…).md` or one with a backtick or quote is only described, never put into a command). `git checkout` is not offered: a change already added or committed is what it would bring back. A project's file is copied only while it really is inside the repository. Copies nothing has pointed at for 37 days, and baselines unused for 30, are let go once a day. Each change is said once. A change of the setting itself is warned the same way (`git rm`, `git rm --cached` or `git mv` of the project's file, an edit of `.project-pm.json`, the guidelines turned off or on, the project's file given up for the person's own, or a setting that cannot be read: `.project-pm.json` not JSON, git not answering), and the baseline then follows the new setting, never comparing the new file with the old one. Putting changes back was tried first and dropped before release: with several sessions at once it could not tell who had changed the file or whether that was agreed, and a wrong guess wrote over the person's own change. It does not catch a change made on purpose to get past it (taking a new baseline by running the hook by hand, deleting the baselines), nor a change a background command makes after a turn ends and before the person speaks again (taken as part of what they let stand).
- A web board, read only: `project-pm serve` serves it and Streamable HTTP MCP on 127.0.0.1 only (port 47130 or the next free one, a 32-byte token, Host and Origin checks, a strict CSP, no CORS), and `project-pm open` starts it when needed and opens the browser. It shows progress, what needs attention, the work items with their QA, each session with its tool, and the agents; it works from phone width to desktop, in dark mode, and says when it is empty or cannot load. `project-pm board` prints the same board in the terminal (`--json` for the data).
- `project-pm init` sets up Claude Code for a project and changes nothing until it is run with `--yes`; it lists every file it would change first. It adds the MCP server (`claude mcp add --scope user`; on Windows it also finds Claude Code installed with npm, a `claude.cmd` file on PATH: it looks for it only in PATH folders on this computer's own disks, never in the project's folder, and runs it through Windows' own `cmd.exe` (System32, whatever `ComSpec` says) in the batch file's own folder, only with arguments `cmd.exe` reads as given), the hooks in `~/.claude/settings.json`, the skill, a section in `AGENTS.md` (one line when the AGENTS.md files near 28 KiB), `@AGENTS.md` at the top of `CLAUDE.md`, a git pre-push hook (one already there becomes `pre-push.local` and runs first), the project's git alias `pm`, and with `--ci` a QA workflow. The single executable copies itself to `~/.project-pm/bin/project-pm-<version>` and every setting points there; nothing touches PATH or the system. With the desktop mod installed, it adds neither the MCP server nor the hooks, which the mod already serves. Someone else's MCP server, alias, skill or workflow is left alone. `project-pm uninstall` undoes it from `install-log.json`: a file nobody touched since comes back byte for byte, one edited since loses only what init put in, what other projects still use stays, and a file that cannot be deleted stays in the log with what to do. On Windows the running program cannot delete itself: once it ends, a hidden script tries once a second for a minute, only ever for a file in `~/.project-pm/bin/`, and if the file is still there then, it opens a note saying so and how to delete it by hand.
- The QA gate in git: the pre-push hook holds a push whose commits no passed or skipped QA covers and names their work items in plain words. `git pm skip "<reason>"` lets one through on the record, on its work item or a new "unregistered push". The board names commits that reached the remote past the hook (`git push --no-verify`). A push the check cannot check (git cannot answer, the data file cannot be read) goes through, since a broken PM must not stop work, but it is said on the spot and listed under *Needs attention* for a week. When the check cannot even tell which project it is in (git does not answer in time), the push goes through with a line on stderr saying it was not checked.
- The QA workflow `init --ci` writes, `.github/workflows/project-pm-qa.yml`, in the core's language: the project's tests (npm, pnpm, yarn or pytest, or a note that there are none), gitleaks over the whole history, osv-scanner on the lockfiles (only high risk fails), and, in a job that installs nothing, the words of the `BLOCKED_TERMS` secret, which are never printed. Each failure is marked on its line and explained in a table in the run's summary. The word scan is a check of its own, so the READMEs say to make both required in branch protection.
- Single executables for Windows x64, macOS arm64 and x64, and Linux x64 and arm64 (Node SEA, about 86 MB, no Node.js needed), built and tested by `.github/workflows/release.yml` on a version tag and published with `SHA256SUMS`. The same workflow can publish the npm package `project-pm` once the repository has an `NPM_TOKEN`; 1.0.0 is not on npm. `core/README.md` and `core/README.zh-TW.md` explain in plain words how to check and allow the unsigned program. `.github/workflows/core.yml` runs the core's tests on Windows, macOS and Linux on every pull request.

### Changed
- While the desktop mod still runs (migration E1), the core reads a project from `~/.project-pm/` first and the mod's `~/.claude/project-pm/` second, and writes both, losing no field either way: when the mod changed an item later, every field the mod does not write comes back from the core's copy; when the core did, a field only a newer mod writes is kept; and `formerOwners` is the union of both. What either side clears on purpose (criteria, a verdict) is not brought back. Like v0.9.1's mod, the core records the owner an item is handed over from in `formerOwners` (once each, only when the owner really changes), so the shared board does not wait on a session that gave its work up. The mod itself is unchanged.
- The core's MCP tools answer in words only by default, without `structuredContent` or `outputSchema`: Claude Code 2.1.326 hands the model the JSON instead of the words when both are there (measured 2026-11-19; design 3.1). `PROJECT_PM_STRUCTURED=1` turns the JSON back on; the web board's `/api/board` and `project-pm board --json` always have it.
- A QA verdict written by the core records the checked commit in full (40 characters); the mod's 7-character ones still match.
- The desktop mod (`.claude-plugin/plugin.json`) and the core share one version from 1.0.0 on (D7), so the mod is 1.0.0 too; the mod itself is unchanged since 0.9.1.

## [0.9.1] - 2026-11-19

### Fixed
- A session a usage limit stopped midway (its last turn ended in error, with words like "You've hit your 5-hour limit · resets 3pm") showed as *Ended*, so nobody came back to it once the limit reset. The mod never looked at how a turn ended: a turn that ends in error carries no answer, the limit's words are only in the transcript, and with its steps ticked the session read as finished. Each session's mod now keeps whether its last turn ended in error (`turn.complete`'s `reason`), the board reads the transcript's `[result] error` line and the words before it, and a new status, *Usage limit · resumes after <time>* (額度用完・<time> 後可續; *Usage limit* when the words give no time), lists it under *Needs attention*, in the counts and on the pane. The model's answer is never read as the error: the turn must have ended in error, and the last words before the transcript's `[result] error` must open, after nothing but punctuation and spaces, the way a usage limit's message does (You've hit your 5-hour or weekly limit, usage limit reached, out of extra usage; in Chinese, 用量, 使用量 or 額度 with 上限 or 用完: 已達用量上限, 額度已用完). Words that only name a limit (為了避免 usage limit exceeded, 已達到上限的檔案), a limit of something else (the context, output or rate limit, a file limit, 上下文長度上限, 速率上限) and other errors (a failing or overloaded API) are not taken for one. It is judged by the words' form alone: if an error left no message of its own and the model's last words happened to open exactly like a usage limit's (Weekly limit reached), they would still be taken for one. A session running again, or whose later turn ended otherwise, is no longer listed, nor is one whose work items have all been handed to another owner or closed: a work item now keeps the owners it was handed over from (`formerOwners`). A new PM rule (15) has the PM pick such a session up once the limit resets, without being reminded: by the quota rules of rule 10, wake a small, warm one, or start a new session that takes over from the hand-over notes, then make the new session the work item's owner.

## [0.9.0] - 2026-11-19

### Added
- The mod enforces QA before a work item closes (docs/design/qa.md). A work item can carry acceptance criteria (`criteria`) and a QA verdict (`qa`: pass, fail or skipped, who checked it, when, and a note), both optional, so items written before keep reading and writing as they were. The ledger takes `criteria`, `qa` (`pass`, `fail`, `skip`), `qa_by` and `qa_note`, and refuses to mark an item done without a pass, or a skip with its reason; whoever checked it may not be its owner (compared trimmed and in any case), and a verdict it cannot record changes nothing. A verdict records the project's HEAD commit and goes when the item gets another owner or is reopened; a close refused beside a verdict keeps the verdict and says so. `force` with a note still closes an item. The board's *Needs attention* lists items awaiting QA (their owner has delivered, or is archived or gone, and there is no verdict) and items that failed QA, each work item's line shows its QA, and the pane shows both counts and each item's verdict. A new rule in the PM's instructions has it write the criteria, and before a code change is pushed start an independent QA agent (Explore, its description leading with "T-xx QA") given only the diff's range and the criteria. The mod adds a QA checklist to such an agent: the diff holds only its target, a bug fix has a test that fails before the fix, tests and validate pass by their exit code, the version and CHANGELOG follow the guidelines, no secret or local setting rides along, and an interface change is looked at on screen; it answers `[pass]` or `[fail]`. New owners are written trimmed, and every check finds an owner trimmed and in any case, items written before included. An open item whose agent owner's record was let go (past the 50 kept) counts as delivered: it awaits QA, and that owner does not hold its close.

A delivery word used as a noun (還沒公開的 commit) no longer reads as work left undone.
- On a session card, the 需追蹤 label ran straight into the recap after it ("需追蹤Merged locally as …"); a full-width space now separates them.
- The commit checked on GitHub was the last hash in the words, which could be one quoted from another project or an example, or part of a session id; with GitHub then unable to answer, the words alone decided. The runs and commits the words name are now tried nearest their own CI words first, a commit only when it is in the session's repository, and the folder's `HEAD` (committed before the words) when none answers.
- A session that left only a push undone stayed *Not released* when its commit went out rebased or squashed with others, since the hash itself never reached a remote branch. The PM now also recognises the commit's content on a remote branch: the files it changed hold its exact content at the branch tip or at one of the branch's later commits, or the same holds for one of its descendants on a local branch (an earlier commit of a squash). Anything else still reads as not pushed.
- The PM lost its `board` and `ledger` tools for good when the engine dropped them after the module's start-up had already run, as when the mod's folder changed and `/board` reloaded it. The PM now checks its tools on every turn and every poll, and registers them again when they are missing.

## [0.3.2] - 2026-10-19

### Added
- CI is checked on GitHub. When a session's latest words say CI is still running, the PM runs `gh` in that session's folder (the run id the words name, else the commit they name, else a `HEAD` committed no later than the words). A pass clears *Waiting on CI*; a failure shows as the new *CI failed* status, is listed under "needs attention", notifies the PM and still blocks the ledger. Answers are cached (a pass for good, a failure for 5 minutes, running or unknown for 1 minute); with no answer, the words decide.
- An open work item's owner stays in sight on the board and in the PM's report whatever its status, including an owner working from another project's folder, shown with its title, status and that it belongs to another project.
- English README with screenshots; the Traditional Chinese README moved to `README.zh-TW.md`.
- An offline demo of the board (`docs/demo/`) that draws the README images from made-up data.
- GitHub Actions workflow that runs `claude plugin validate .` and `claude plugin test .`.

### Changed
- A recap counts only for the turn whose `wrap_up` wrote it; a later turn that ends without its own `wrap_up` drops it.
- A session record that has missed later turns gives way to the transcript's last message.

### Fixed
- A session whose record was empty (written when its module reloaded) showed as ended even when its transcript said CI was still running; empty records are now ignored and the transcript decides.
- A recap saying nothing is left, such as 沒有任何未提交的修改 ("there are no uncommitted changes"), was flagged as unfinished work.
- After `/reload-plugins` the PM lost its `board` and `ledger` tools until the session restarted; start-up now runs on the first hook a fresh module copy sees, so the tools return on the PM's next turn.
- An owner working from another project's folder was reported as lost; only an archived or missing owner is now.

## [0.3.1] - 2026-10-19

### Fixed
- After a module reload, a session stopped writing its record: the host kept who the session was, but the module's own record was gone and was never loaded again.
- A session the desktop app had not registered yet at its start was never tracked; it now asks again, at most every 30 seconds, on its next tracked event.

## [0.3.0] - 2026-10-17

### Added
- *Waiting on CI* status: a session whose latest turn says CI has not finished never decays into *Ended*, however long it sits, and is listed under "needs attention".
- The ledger refuses to close a work item whose owner is waiting on CI, running, waiting on the person or stopped mid-task, unless the person explicitly confirms (`force` with a note).

## [0.2.1] - 2026-10-17

### Added
- First public version: one PM session per project (`/pm`, `/pm off`), tracking every session's task list, final recap, open question, latest prompt and last answer.
- Project board pane (`/board`): completion ring, running / waiting-on-you / unfinished counters, session cards with step bars, this project or all projects, archive with confirmation.
- The PM's `board` report and `ledger` of work items (T-01, T-02, …).
- A band above the prompt in projects without a PM, offering to start a PM session or make the current one the PM.
- Notifications to the PM when a session starts waiting on the person or stops with steps left.
